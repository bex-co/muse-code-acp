# 013 — Verify additional workspace roots on Muse 1.4.12

Why: the w1/008 watch trigger looks met (public `workspaceRoots` on `session/start`/`turn/start`, present since SDK 1.4.8), so ACP `additionalDirectories` may be deliverable natively instead of staying unsupported.

Estimate: 1h verification; promote to a milestone if it holds. Source: SDK 1.4.12 bump re-check of w1/008, 2026-10-23.

- Evidence so far: Muse 1.4.12-R6909.1 accepted `workspaceRoots: [ws, extra]` on a throwaway session. The schema says every root gets the `:workspace_roots` sandbox rules and extra roots grant no Project Trust.
- Still unverified: allowed writes inside an extra root and denied writes outside all roots, under the sandbox; whether roots survive restart/resume and host reuse (w1/008 acceptance).
- No widening to a common ancestor or disabling the sandbox (w1/008, DO_NOT_DO).

## Done (2026-10-27)

Implemented. Evidence (Muse 1.4.13-R6996.1, loopback, default sandbox): extra-root writes allowed without escalation, writes outside all roots denied (`write_file` policy) or sandbox-blocked (bash), roots persisted across host restart/resume and inherited by forks, `turn/start.workspaceRoots` replaces the set (revocation sticks). ACP 1.8 `additionalDirectories` is stable on new/load/resume/fork. Design: `src/workspace-roots.ts` (canonicalize, dedupe, drop cwd; early refusal on exec/older hosts), gate `supportsWorkspaceRoots` (1.4.13+), capability advertised, every turn sends `[cwd, ...extra]`, applied set persisted in session preferences (forks copy the source's), `/goal set|resume` refused until applied. Tests: `workspace-roots.test.ts` (capability, canonical roots per turn, clear on resume, invalid paths, goal guard), updated availability/fork/resume tests, `workspace-roots-live.test.ts` on 1.4.13 (extra written, outside blocked, cleared after resume without the field).
