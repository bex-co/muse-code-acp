## Objective

Evidence for which of recap/request, recap/cancel, recap/completed (1.4.6); session/rename (1.3.0); session/nameChanged (folded, currently ignored) the installed host completes, with exact request/response shapes.

## Context

- `/rename` sets an adapter-owned title (`src/session-title.ts`); `session/nameChanged` is classified as ignored in `src/muse-view-events.ts`; recap is new in 1.4.6.
- Use the loopback provider and isolated directories; no paid tokens.
- Depends on w3/m7 so verification runs on Muse 1.4.6 with SDK 1.4.6.

## Steps

1. Probe each method through the public SDK connection and record outcomes, errors and resulting folded events/items.
2. Record which hosts/versions support each operation and any refusal kinds.

## Evidence

Muse 1.4.7-R6101.1, public SDK connection with a notification tee, loopback provider, no paid tokens:

| Case                                  | Result                                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `recap/request` after two turns       | accepted; one model side-call ("The user stepped away…"); `recap/completed` `completed` with text  |
| `recap/request` on an empty session   | accepted; `recap/completed` `failed` `providerFailed`                                              |
| `recap/cancel` idle                   | accepted                                                                                           |
| `session/rename "Probe Session Name"` | accepted, canonical name `probe session name`; `session/nameChanged` folded (`nameOrigin: custom`) |
| `session/rename "   "`                | accepted with a blank name (adapter must validate)                                                 |

`recap/completed` is not folded and the connection has a single notification slot, so the host tees it before the SDK client installs its router.
