## Objective

Know what `muse exec` is waiting for when it stalls.

## Context

- Reproduction from w3/004: Default mode, loopback provider, scripted `bash` write refused by the reviewer, then no events and no exit within 180 s (Muse 1.4.4-R5419.1).
- Suspect: Muse's reminder requests offer only `submit_reminder_decision`, and the loopback stub (`src/tests/loopback-provider.ts`) answers them with plain text.
- Upstream [#63](https://github.com/meta-models/muse-code-sdk/issues/63) reports a different SDK `denyUnmatched` reminder denial, fixed in host 1.4.2. Compare reminder decision/terminal records, but do not assume it explains this 1.4.4 Default-mode exec observation.

## Steps

1. In an isolated workspace and home/config/data directory, rerun with the loopback provider, unchanged Default-mode approval/sandbox flags, and a bounded probe deadline. Record every provider request (tools offered, last input item, response sent) with timestamps until the stall; stop and reap the owned process after the capture deadline.
2. Inspect the session with `muse trace` (or the session log), including reminder-child records, to find the last record and any pending work. Preserve public-safe excerpts and elapsed times in the milestone evidence.

- Requests: #1 reminder observer (offers only `submit_reminder_decision`) → stub replied text; #2 main agent → stub's scripted `bash` write; #6/#8/#10 **approval reviewer** (offers `read_file, search, bash, submit_approval_assessment`) → the stub also injected its scripted `bash` write there, which Muse refused ("approval reviewer bash accepts only foreground read-only inspection commands …"); #7/#9/#11 → stub replied text. The reviewer never called `submit_approval_assessment`.
