# 011 — Show Muse reviewer activity while an approval is held

Why: Muse 1.4.12 announces when its built-in reviewer is judging a tool call (`approval/reviewing`, `approval/updated` `reviewStarted`/`reviewCompleted`), but ACP clients see only a silent wait until a permission prompt or the tool result arrives.

Estimate: about 1h for the surface decision plus a gated live test; promote if it grows. Source: SDK 1.4.12 bump, 2026-10-23.

- Evidence (Muse 1.4.12-R6909.1, loopback reviewer, probe on 2026-10-23): `approval/reviewing` → `approval/updated reviewStarted` → `approval/request` (server request) → `approval/updated reviewCompleted` → `approval/requested`. The SDK fold exposes `approval/reviewing` as `{kind: "approvalReviewing", approvalId}`, with no decision open. `src/muse-view-events.ts` currently ignores it and points here.
- Surface: an ACP `Notice` for clients advertising `session.notices`, or `muse/approval` `_meta`. Never open an ACP permission request for a reviewing approval (DO_NOT_DO: only real gates prompt).
- Check that reviewer time is not counted as a stall by `pending-watchdog.ts`.
- Optional: SDK 1.4.12 `cuaCardFacts` on computer-use approvals could enrich permission titles.

## Done (2026-10-27)

Implemented as ACP `notice` updates for clients advertising `session.notices` (`src/turn-notices.ts`; host notification tee in `src/muse-sdk-host.ts`; scoped to the running turn, falling back to the fold's active turn before `sendUserTurn` resolves). Others get nothing. Tests: `turn-notices.test.ts` (both notices, older-turn retry ignored, non-negotiating client gets none) and `notices-live.test.ts` on Muse 1.4.13-R6996.1 (503 loopback retries; escalated reviewer hold), registered in `test:muse-loopback`.
