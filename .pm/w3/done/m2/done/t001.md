## Objective

Find why forking at a real completed turn is rejected on Muse 1.4.3.

## Context

- `src/tests/session-fork-live.test.ts` fails on `main` (`3ea3213`) with host `1.4.3-R5018.1`: `_meta["muse/fork"].lastTurnId = firstTurn` (taken from `muse/activeTurnId`) returns `forkBoundaryInvalid`. Root cause unknown; may affect users of `muse/fork` with `lastTurnId`.
- Start at `src/session-fork.ts:60`; compare the turn id from `muse/activeTurnId` with turn ids in `session/read` history on 1.4.3, and the SDK fork request shape.

## Steps

1. Reproduce with the loopback provider (no paid tokens) and capture the raw host error and the ids involved.
2. Determine whether the adapter reports the wrong id, the host changed boundary rules, or the test timing is wrong.

## Evidence

Muse `1.4.3-R5018.1`, loopback provider, no paid tokens. A probe ran three turns through the adapter, then called public `session/fork` on a control host for each turn ID reported in `muse/activeTurnId`:

- turn 1 and turn 2 (completed, present in the session log): `MspError forkBoundaryInvalid`, message `invalid fork boundary for session …: InvalidCut`, `data: { kind: "forkBoundaryInvalid", retryable: false, sessionId, lastTurnId }`;
- turn 3 (`session/read` `lastTurn: { turnId, terminal: "completed" }`): fork succeeds.

The adapter reports correct IDs. The host's own exported schema (`muse schema generate-ts`) still documents `ForkCutPoint.lastTurnId` as "the last completed turn to copy, inclusive", so rejecting earlier completed turns is a host regression. No older host binary was installed to compare (the launcher keeps only the active version).
