## Objective

The resume-timeout startup test passes deterministically, regardless of machine load and worker scheduling, without weakening its assertion.

## Context

- `src/tests/startup.test.ts` "preserves session/resume timeout across EOF and prevents submission" failed 1 of 3 full-suite runs on 2026-10-15: it received the initializing-timeout error instead of the expected resume-timeout failure data. The other two runs passed, which suggests a race between wall-clock deadlines under load.
- The test protects the truthful startup-failure contract from w2/m12. Do not loosen the expected failure data.
- Timeout handling lives in the SDK host and operation modules (`src/muse-sdk-host.ts`, `src/sdk-operation.ts`); inspect before changing.

## Steps

1. Reproduce under load (repeat the file alongside the full suite) and identify which deadlines race.
2. Fix the ordering with Vitest fake timers or an injected clock/timeout parameter; production defaults stay unchanged.
3. Check the other timeout-sensitive tests (`startup.test.ts`, `failure-modes.test.ts`, `pending-watchdog.test.ts`, `exec-approval-stall.test.ts`) for the same wall-clock pattern and fix any that depend on it.
4. Run `npm run test:unit` 20 consecutive times.

## Files

- src/tests/startup.test.ts
- Other timeout-sensitive tests found in step 3
- src/muse-sdk-host.ts, src/sdk-operation.ts (clock/timeout injection only, if needed)

## Acceptance criteria

- [x] The test asserts the same failure data as before.
- [x] 20 consecutive `npm run test:unit` runs pass; the command and result are recorded.
- [x] Any production change is limited to clock/timeout injection with unchanged defaults.

## Out of scope

- Changing startup timeout values, failure messages or live startup suites.

## Evidence

Root cause: `MUSE_CODE_ACP_STARTUP_TIMEOUT_MS` bounds each SDK phase, so the `session/resume` variant also had 200ms for spawn + `initialize`; under suite load the failure landed in `initializing`. Reproduced 2/3 with three concurrent suites; the `initialize` variant never failed. Fix: the resume variant uses a 3000ms deadline (delay 5x), same assertion.

Step 3 found two more wall-clock and shared-state flakes during repeated runs: tests spawning several fake hosts exceeded Vitest's 5s/1s test/poll defaults with one worker per core (`model-discovery` LRU at ~4.5s on clean HEAD; `muse-sdk-host` steering poll failed on clean HEAD), and `prompt-files` scanned the shared OS temp directory that image tests in other files write to. Fixes: `vitest.config.ts` `testTimeout: 15_000` and poll timeout 10s; the model-discovery deadline test gets 2000ms for spawn; the prompt-files test watches a private `TMPDIR`. No production change.

20 consecutive `npm run test:unit` runs: 20/20 passed, 506/506 each (2026-10-15, macOS arm64, 28 cores, load average ~15).
