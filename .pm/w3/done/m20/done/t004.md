## Objective

Opening a thread starts Muse in the background, so the first prompt does not wait ~12 s for `session/start` and the model picker lists Muse's catalog without `/models`.

## Acceptance criteria

- [x] After `session/new` and `session/load` on the SDK backend, the per-session host opens in the background with the session's current configuration; the first prompt reuses it, a changed configuration replaces it, failures surface on the first prompt as today, and an unused host closes on the idle timer.
- [x] The catalog arrives as `config_option_update` without a prompt.
- [x] Deterministic tests for reuse, replacement and failure; the live suites still pass.
- [x] Measured on the maintainer machine: first-prompt wait before vs after.

## Evidence (2026-10-25)

`MuseSdkHost.prewarm` plus `prewarmSdkHost`/`ensureSdkHost` (`src/sdk-prompt-turn.ts`); the agent prewarms after new/load/resume/fork, idle config and mode changes, and catalog publications that settle the route. A prewarm never commits the route to the session, never replaces a host serving a turn (`turnFinished`/`activeTurn`), and does not reapply the startup policy on the first acquire. Tests: `prewarm.test.ts` (catalog before the prompt, one reopen for a profiled catalog then reuse, background reopen after a mode change, dispose closes it). Real host: `startup-live` populated-history run on 1.4.13 ends with exactly 16 spawned hosts for 16 sessions (reuse, no catalog-only host); `session/new` < 5 s. Measured: Muse `session/start` alone is 11.7 s on the maintainer home (initialize 0.74 s, resume probe 1.4 s). Test infrastructure: `ensureExecutable` stops parallel suites from bumping the shared fixture's ctime (part of the host identity), and fake-host suites default to no prewarm (`prewarm: true` opts in).
