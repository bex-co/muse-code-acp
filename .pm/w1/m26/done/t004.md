## Objective

When Muse's automated reviewer escalates a tool call to the user, the ACP permission prompt shows the reviewer's reason.

## Context

- `ApprovalRequest.reviewerReason` (SDK 1.4.14) is a single bounded display line. It is present only when a structured `escalate` with a rationale released the request, and it "never authorizes anything". The SDK facade keeps it across stages.
- `src/muse-permissions.ts` builds `session/request_permission` from host-provided choices only (`.pm/DO_NOT_DO.md`).

## Steps

1. Add the reason to the permission request's display content (e.g. "Muse's reviewer asked you: <reason>") when present; leave the options untouched.
2. Fake-msp coverage, with and without the field.
3. Try a real escalation (exec-reviewer setup in the loopback suites, or a real provider). Record the evidence, or record that it is schema-only.

## Files

- `src/muse-permissions.ts`, `src/tests/fixtures/fake-msp.cjs`, `src/tests/muse-permissions*.test.ts`

## Acceptance criteria

- [x] With `reviewerReason`, the prompt shows it; without it, the prompt is byte-identical to today's.
- [x] Options and outcomes are unchanged; cancellation still never grants.

## Out of scope

- Using the reason for any decision.

## Evidence

- `src/muse-permissions.ts`: a non-blank `reviewerReason` adds `toolCall.content` ("Muse's reviewer asks you to decide: <reason>") and `muse/approval.reviewerReason`. Options are untouched. A blank or missing reason leaves the request identical (unit test in `permissions.test.ts`).
- Real host: `notices-live.test.ts` asserts the content on ≥1.4.14. Muse 1.4.14-R7309.1 sent `"judgeEscalated":true,"reviewerReason":"loopback provider review"` for the loopback reviewer's escalation, and the test passes (full 1.4.14 loopback 72/72).
