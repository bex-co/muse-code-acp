## Objective

Give ACP-client-provided MCP servers a path into Muse — via a scoped settings overlay if one exists, or a project-config write with user consent — and if neither is safe, reject them cleanly with a documented reason.

## Context

- Impedance mismatch from research: ACP clients pass MCP servers per-session (stdio/http); Muse 0.2.1 reads `mcp_servers` only from its settings file (`transport: stdio|streamable_http`, `mode: required|optional`) — no per-run flag observed.
- Investigate in order: (1) a project-level settings/config file muse merges (check `muse init` scaffold + `muse config` planes for a workspace-scoped document); (2) `--agents <JSON>` ephemeral overlay (probe whether it can carry MCP config); (3) `XDG_CONFIG_HOME` redirection to a generated config dir (heavy — it would shadow the user's model/auth settings; only with full inheritance).
- Never write `~/.config/muse/settings.json` (user's file). Any workspace file written must be disclosed and idempotent.
- Fallback: reject session-provided MCP servers with a clear message and set `mcpCapabilities` to empty — honest per DO_NOT_DO.

## Steps

1. Probe the three mechanisms against muse 0.2.1; record findings in a `docs/mcp-passthrough.md` decision note.
2. Implement the best viable mechanism (translation ACP MCP config → muse `mcp_servers` schema, `mode: optional` so a dead server doesn't abort runs), or the clean rejection path.
3. Tests: config translation shapes; if overlay shipped, an integration test with a trivial stdio MCP server.

## Acceptance criteria

- [ ] Decision note records what was probed, what worked, and why the shipped mechanism was chosen
- [ ] Advertised `mcpCapabilities` exactly match reality (http only if streamable_http passthrough works, etc.)
- [ ] User's `~/.config/muse/settings.json` is never modified (asserted in tests via temp HOME)

## Out of scope

- Muse's own MCP servers configured in user settings (they just work; nothing to do)
