## Objective

Make ACP configuration reflect the model and execution policy Muse actually uses, preventing mode/config regressions at default cutover.

## Context

- Current config selections are stored locally and applied on the next per-turn host; SDK modes currently include only default/readOnly.
- Reference session-config-options.test.ts checks rejected selections, model/effort compatibility, and consistent updates across configuration surfaces.

## Steps

1. Read supported effective model/config information from documented SDK state and apply selections at the promised next-turn boundary.
2. Validate model/effort combinations using available host metadata and preserve a compatible effort or choose the documented default; handle backend rejection without reporting a successful change.
3. Update mode descriptions for SDK semantics and verify actual readOnly enforcement; keep unsupported bypass/yolo modes absent from SDK mode lists while preserving legacy guards.
4. Test load/resume configuration, selection notifications where required, changes during active turns, and invalid/unsupported selections through ACP.

## Acceptance criteria

- [ ] The next MSP turn uses the selected supported model/effort, and ACP-reported values agree with the effective host behavior.
- [ ] Invalid selections and backend rejections leave the previous valid configuration intact or report a clearly documented failure before execution.
- [ ] SDK readOnly prevents the promised writes/shell actions; unsupported dangerous modes are not advertised or silently translated to weaker policy.
- [ ] Loaded configuration follows the documented persistence/reset policy and does not silently replace stored supported model state with an unrelated default.

## Out of scope

- Emulating unavailable safety flags, changing default sandbox protections, and requiring unsupported legacy dangerous-mode parity.
