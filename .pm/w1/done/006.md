# 006 — Future: Observable native scheduled retries

Why: retain the missing native capability for a future public SDK/host change without blocking current w2 delivery.

Estimate: 30m for one bounded reassessment when triggered; implementation requires
promotion back into w2 with appropriately sized tasks, not work hidden in this note.

## Evidence and current boundary

Fresh 1.2.1 HTTP 503 recheck also completed with retryable modelError and no turn/retryScheduled, despite 20 provider requests including subordinate activity.

Source slices: w1/m14/t003.
Full original acceptance and [current/future allocation](../ownership-2026-09-14.md)
are preserved. This note is not a completed feature or a duplicate implementation task.

## Revisit trigger

A release or public supported scenario emits the actual non-terminal retry scheduling event with attempt/delay and terminal behavior.

Do not poll repeatedly without a new public artifact or concrete supported repro.
Uncertainty alone is not proof of impossibility; if a currently supported route is
found, immediately move that delivery scope into w2 and remove this duplicate watch.

## Acceptance after support appears

Verify scheduling through success/exhaustion and close/cancel; preserve original ACP prompt. Do not invent progress from HTTP retries or add adapter replay.

Verify both public admission and user-visible outcome before advertising. Promote
implementation with adoption, simplification, required real-host CI and closeout;
keep blocked variants explicit. No private APIs, TUI automation or fake outcomes.
