## Objective

Advertise the user's Muse skills (built-in `/plan`, `/grilling`, `/taste`, … plus user/project skills) as ACP slash commands, and make invoking one actually trigger the skill in the next exec turn.

## Context

- Enumeration: `muse skills list` (add `--source all` for diagnostics); skills live in `$XDG_CONFIG_HOME/muse/skills`, `~/.agents/skills`, `<repo>/.agents/skills/`, legacy `.codex/skills`/`.claude/skills`. Parse the CLI output (check for a `--format json` option first; fall back to text parsing).
- Open question flagged in research: whether a `/skill` slash prefix in the `muse exec` prompt text triggers skill loading in headless mode (skills are "explicit invocation only" and lazily loaded via a read-skill tool call in the TUI). Verify empirically first — if exec ignores slash syntax, prepend an instruction line referencing the skill instead, and record which mechanism shipped.
- Filter to skills that make sense headlessly; keep a small blocklist for TUI-only ones (pattern: claude-agent-acp `UNSUPPORTED_COMMANDS`, `acp-agent.ts:7480-7519`).

## Steps

1. Empirically verify skill invocation under `muse exec` (echo provider won't exercise skills — one cheap real-provider probe with `/plan`).
2. Implement skills enumeration + ACP `available_commands` advertisement per session (workspace-scoped skills differ per cwd).
3. Map incoming ACP command invocations → prompt-text construction for the next exec.
4. Tests: enumeration parsing (fixture of `muse skills list` output), command → prompt mapping, blocklist.
