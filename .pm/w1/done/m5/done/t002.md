## Objective

Prevent a delayed or ambiguous approval from authorizing another tool or turn, especially when multiple MCP requests share a server or tool name.

## Context

- Reference PermissionLifecycleContext.test.ts covers turn-boundary reset, session-scoped IDs, and generation isolation.
- Per-turn Muse hosts may limit approval persistence; only a tested host-supported scope may be offered.

## Steps

1. Scope pending requests by session, turn/generation, request ID, and tool call ID; avoid correlation by tool or MCP server name alone.
2. Discard or reject stale, duplicate, and already-resolved replies without granting or allocating a new authorization.
3. Dispose pending state on completion, cancel, transport closure, and failure; ensure late callbacks cannot affect a restarted session.
4. Test multiple concurrent requests, repeated tool names, allow-once scope, and any host-provided persistent scope across the lifetime actually claimed.

## Acceptance criteria

- [ ] Resolving request B never resolves A, including requests from the same MCP server with the same tool name.
- [ ] A late response from a completed/cancelled turn cannot send a valid decision for the next turn.
- [ ] Duplicate backend events or client responses cause at most one logical approval decision and one protected execution.
- [ ] Offered option labels and scope match tested host behavior; unsupported persistence is not advertised.

## Out of scope

- A separate adapter-owned permission policy engine and emulating unsupported allow-always semantics.
