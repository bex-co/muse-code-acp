## Objective

Validate the complete ACP-to-SDK-to-Muse permission path against observable file/command effects, beyond a scripted protocol transcript.

## Context

- src/tests/muse-sdk-live.test.ts already uses a real local Muse host and a loopback provider with dummy credentials.
- Reference e2e/acp-e2e-shell-approval.test.ts and e2e/acp-e2e-mcp-approval.test.ts verify effects and scope. Use their behavioral pattern with a deterministic local provider.

## Steps

1. Extend the loopback provider to request a harmless tool that writes a marker only inside a disposable workspace, using a documented host configuration that actually requires client approval.
2. Drive the built ACP entrypoint over stdio and hold the permission response until the test verifies the marker is absent.
3. Exercise allow, deny, cancel, and late/stale response cases and observe the actual marker/tool count; include a local MCP tool if it uses a distinct approval path.
4. Record the tested host version/capabilities and make explicitly selected real-host tests fail clearly if required support or the binary is missing.

## Acceptance criteria

- [ ] Before approval the protected marker is absent; after allow it appears exactly once; deny and cancel leave it absent.
- [ ] The approval passes through actual ACP stdio, the public SDK, and a real Muse child, using only local provider traffic and dummy credentials.
- [ ] A cancelled request cannot be executed by a delayed allow, and the next prompt remains usable.
- [ ] Required execution-gating scenarios run rather than skip; host limitations are recorded as unfinished acceptance work instead of a passing fake-host substitute.

## Out of scope

- Paid provider calls, host-global settings changes, TUI automation, and bypassing approvals to make the test pass.
