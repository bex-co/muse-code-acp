## Objective

Handle Muse requests for user input without confusing them with tool authorization or leaving an ACP prompt waiting indefinitely.

## Context

- The minimal SDK backend currently throws on userInput/requested.
- Use m4's published ACP/MSP type matrix and the reference elicitation-events.test.ts. Form support, URL support, and tool permissions are separate protocol contracts.

## Steps

1. Expose the standard client elicitation method through the connection seam for the modes supported by the pinned ACP SDK.
2. Translate supported MSP input schemas and answers using exported types; preserve required fields, choice IDs, and free-text values.
3. Validate replies and handle decline, dismissal, cancellation, unsupported required fields, and clients with no compatible elicitation mode.
4. Keep user-input lifecycle state distinct from approvals and add wire tests for valid, invalid, concurrent, and stale answers; support URL requests only if the host actually emits a declared compatible shape.

## Acceptance criteria

- [ ] A supported structured request is displayed through ACP and a validated answer reaches the matching MSP request.
- [ ] Absent/empty client capability objects do not accidentally enable unsupported elicitation modes.
- [ ] Malformed replies, dismissal, and unsupported schemas do not grant permission or leave a pending request unresolved.
- [ ] Cancellation disposes the input request and later answers cannot reach a subsequent turn.
- [ ] If the selected package version lacks a required standard type, use a documented compatible release identified by the support matrix; do not invent an extension to mark the task complete.

## Out of scope

- Custom editor forms, AIR-only APIs, and using permission approval as an unrestricted free-text input substitute.
