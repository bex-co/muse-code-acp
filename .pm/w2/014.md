# 014 — Investigate execution-host startup latency under concurrent ACP load

Why: Successful SDK initialization frequently approaches the current startup deadline and dominates session setup time for automated multi-session clients.

## Evidence

Observed with adapter `06fd6f7`, SDK 0.1.1 and Muse `1.3.0-R3057.1` on 2026-09-14 local time / 2026-09-15 UTC, with up to 16 host-managed review assignments in parallel.

The following snapshot was computed from the persisted adapter phase log. Samples are completed transitions only; active and failed phases are excluded. These are adapter phase durations, not independently instrumented native-host internals.

| Completed phase | Samples | Median    | P95        | Maximum    |
| --------------- | ------- | --------- | ---------- | ---------- |
| initializing    | 293     | 63,865 ms | 118,427 ms | 119,991 ms |
| preparing       | 293     | 740 ms    | 2,083 ms   | 2,715 ms   |
| submitting      | 293     | 124 ms    | 439 ms     | 1,000 ms   |

Method: extract milliseconds from `phase <phase>: <milliseconds>ms; entering <different-phase>`, sort each phase's values, select median at index `n // 2` and P95 at `floor(0.95 * (n - 1))`. The log was still growing; these figures are not final-run totals.

Exact slow-initialization excerpts copied from the persisted log:

```text
2026-09-15T05:09:10.131Z pid=17344 muse-sdk phase initializing: 119991ms; entering preparing
2026-09-15T05:09:10.150Z pid=17349 muse-sdk phase initializing: 119951ms; entering preparing
2026-09-15T05:15:31.575Z pid=29022 muse-sdk phase initializing: 119989ms; entering preparing
```

At this revision, [src/sdk-operation.ts](../../src/sdk-operation.ts) defaults the startup deadline to 120,000 ms. These samples completed successfully just below that limit; they do **not** prove startup timeouts occurred. The run continued making review progress. Later provider 429 retries were also observed, but are not established as the cause of initialization latency.

## Attribution and scope

This is an adapter performance investigation, not a confirmed claim that the adapter causes all native-host delay. [src/muse-sdk-host.ts](../../src/muse-sdk-host.ts) owns the public SDK handshake; the caller also creates a fresh ACP process for each assignment. Measure native-host baseline, adapter orchestration and caller lifecycle separately before choosing where a fix belongs. Coordinate catalog-host overhead with [013 / m13](done/m13/README.md).

## Experimental attribution and upstream tracking (2026-09-15 UTC)

**Status:** native startup cause reproduced; upstream fix pending in [meta-models/muse-code-sdk #11](https://github.com/meta-models/muse-code-sdk/issues/11). Adapter mitigation is delivered and validated separately in [m13](done/m13/README.md); this note remains open until the native fix is available and rechecked.

The [public reproduction](../../scripts/reproduce-muse-startup.mjs) generates 6,000 content-free history directories with isolated dummy credentials and no inference. Direct SDK-only initialization measured 80 ms with empty history, 998 ms with populated history at concurrency 1, and 11,831–12,023 ms with populated history at concurrency 16. Moving exactly the same files outside `muse/sessions` reduced initialization to 57 ms. `model/list` took 0–4 ms. All provider HTTP counters were zero. See [method and limitations](../../docs/muse-startup-latency.md).

Native samples show main-thread directory traversal before initialization; the precise native routine and remedy require upstream work. The existing host population and a controlled host using existing data showed the same traversal. A controlled SDK-only initialization against existing data took 81.368 seconds while model/list took 3 ms; no private history contents were copied into the reproduction.

Remaining work: track upstream's public fix, rerun the synthetic empty/populated and 1/16 matrix on that fixed version, then close only with measured improvement and no session-visibility regression. Do not close this note merely because m13 removes extra catalog-only hosts. Existing m12 cause/cancellation behavior remains required.
